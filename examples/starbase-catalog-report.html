02 / Executive summary

One truth. Many read shapes.

The important boundary is not a service boundary. It is the point where unstable source evidence becomes stable canonical contracts.

StarBase keeps the expensive reasoning in the write path, so consumers receive a narrow, typed, read-optimized surface.
Extraction, merging, provenance, enrichment, and projection are allowed to be complex. Advisor workflows are not: they depend on the query SDK and the materialized views it composes.

03 / Governing seam

Write broad. Read narrow.

The package’s strongest architectural decision is an asymmetric API: production can see every source-specific detail; consumers see only stable contracts and projections.

Write / ingestion

Source adapters and orchestration own volatility. They fetch, reconcile, enrich, persist, project, and record consistency evidence.

  • Dependency-injected SDK clients
  • Pure canonical build step
  • Content-hash-gated writes
  • Retry and checkpoint ownership

Read / consumption

The query layer composes point reads, lineage, search, and pre-rolled views behind one typed in-process facade.

  • Presentation-neutral contracts
  • Optional search capability
  • Explicit client lifecycle
  • No ingestion dependency in Advisor

05 / Load-bearing invariants

What must remain true.

These are the constraints that make reruns safe and the catalog trustworthy—not incidental implementation details.

Canonical before clever

LLM output may improve prose, but it cannot assign the structural domain. Domain remains a deterministic builder concern.

Hashes gate mutation

Canonical writes and every projector carry stable content or input hashes, keeping unchanged reruns cheap and idempotent.

Upsert before delete

Projection cleanup runs only after successful materialization and uses caps plus empty-source guards to avoid destructive transient states.

Order has an owner

The orchestrator owns sequencing, retries, consistency, and manifests; concrete Azure clients remain injected at the CLI boundary.
